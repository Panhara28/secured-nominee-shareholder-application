## 2026-09-13 (round 6 - found and fixed the real UAT login blocker, baked the fix into deploy)
- After the API repo's comprehensive UAT reseed, the live site's login kept 500ing. A long detour through DB-server disk-space/network theories (see the API repo's history for that) turned out to be a red herring for the *actual* blocker here: this app's own container couldn't resolve the API container by name at all. Confirmed via this container's logs — `TypeError: fetch failed ... getaddrinfo ENOTFOUND secured-nominee-shareholder-api-uat` — while raw IP-to-IP traffic between the two containers worked fine throughout. Root cause: both UAT containers were only on Docker's default `bridge` network, which doesn't do container-name DNS (only user-defined networks do), and `API_BASE_URL` is set to `http://secured-nominee-shareholder-api-uat:8080`.
- Fixed live by connecting both running containers to `nominee-net` (a pre-existing, previously-unused custom network on the host) via `docker network connect` — no rebuild/restart needed. Verified end-to-end: admin/reviewer/shareholder logins all succeed via `https://demo-nominee.moc.gov.kh`, stable across repeated requests.
- Baked the fix into the deploy workflow so a future full container recreation doesn't silently lose it again: added `scripts/ensure-nominee-net.sh` (idempotent, retries SSH up to 5 times — this host's SSH access has been intermittently flaky) plus `deploy:uat`/`postdeploy:uat` npm scripts, so `npm run deploy:uat` runs `pongreay uat` and then automatically re-attaches both containers to `nominee-net`. `pongreay` itself has no `--network` option or deploy hooks (shared global CLI used by other unrelated projects on this host, so left unmodified) — this per-repo npm hook is the practical equivalent. Same script/scripts pair added to the API repo too.
