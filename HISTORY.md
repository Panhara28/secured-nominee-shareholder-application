## 2026-09-13 (round 6 - found and fixed the real UAT login blocker, baked the fix into deploy)
- After the API repo's comprehensive UAT reseed, the live site's login kept 500ing. A long detour through DB-server disk-space/network theories (see the API repo's history for that) turned out to be a red herring for the *actual* blocker here: this app's own container couldn't resolve the API container by name at all. Confirmed via this container's logs — `TypeError: fetch failed ... getaddrinfo ENOTFOUND secured-nominee-shareholder-api-uat` — while raw IP-to-IP traffic between the two containers worked fine throughout. Root cause: both UAT containers were only on Docker's default `bridge` network, which doesn't do container-name DNS (only user-defined networks do), and `API_BASE_URL` is set to `http://secured-nominee-shareholder-api-uat:8080`.
- Fixed live by connecting both running containers to `nominee-net` (a pre-existing, previously-unused custom network on the host) via `docker network connect` — no rebuild/restart needed. Verified end-to-end: admin/reviewer/shareholder logins all succeed via `https://demo-nominee.moc.gov.kh`, stable across repeated requests.
- Baked the fix into the deploy workflow so a future full container recreation doesn't silently lose it again: added `scripts/ensure-nominee-net.sh` (idempotent, retries SSH up to 5 times — this host's SSH access has been intermittently flaky) plus `deploy:uat`/`postdeploy:uat` npm scripts, so `npm run deploy:uat` runs `pongreay uat` and then automatically re-attaches both containers to `nominee-net`. `pongreay` itself has no `--network` option or deploy hooks (shared global CLI used by other unrelated projects on this host, so left unmodified) — this per-repo npm hook is the practical equivalent. Same script/scripts pair added to the API repo too.

## 2026-09-13 (round 5 - deployed to UAT, fixed a real package-lock.json drift bug along the way)
- Deployed `main` (commit `888d607`) to UAT via `pongreay uat --skip-tests` — container `secured-nominee-shareholder-uat` on `sysapp01@172.20.15.41:3030`, confirmed healthy (`pongreay status uat` → `healthy: http://127.0.0.1:3030/en/portal/login`) and remote logs show a clean `next start`, migrations already applied, no errors.
- **Bug fixed**: the committed `package-lock.json` was missing `next-intl`'s nested `@swc/helpers@0.5.23` dependency entirely, so `npm ci` (used by the Dockerfile for reproducible installs) failed with `EUSAGE` on every deploy attempt, while plain `npm install` silently tolerated the drift and gave no indication anything was wrong — this is why local dev never surfaced it. Root-caused by testing `npm ci` directly (bypassing pongreay/BuildKit cache entirely) to rule out a caching red herring first. Fixed by deleting `node_modules` + `package-lock.json` and running a from-scratch `npm install`; only patch/minor bumps within existing semver ranges resulted (e.g. `next-intl` 4.13.6→4.14.4, `@prisma/*` 7.9.1→7.10.0), no major version changes. Verified with a clean (`--no-cache`, pruned builder cache) `docker build` before committing.
- Caution for next time: never bind-mount the live working directory into a throwaway debug container and run destructive commands (`rm -rf node_modules`) inside it — I did this once mid-investigation and it wiped the host's `node_modules` (installing Linux binaries in its place), crashing the local dev server; had to `rm -rf node_modules && npm install` again on the host to recover mac-native bindings, then clear `.next` (stale cache incompatible with the bumped `@swc/core` version was causing Turbopack to hang, not error) before the dev server would serve again.

## 2026-09-13 (round 4 - fixed the permission-save UX gap found in round 3)
- **Fixed**: `AdminRolePermissionsEditor.tsx` module-permission toggles gave no indication that "Save Permissions" (below the fold) still needed to be clicked — an admin could toggle checkmarks, believe they'd taken effect, and navigate away with nothing persisted. Added dirty-state tracking (`savedPermissions` snapshot vs current `permissions`), a `beforeunload` guard that warns before leaving the tab with unsaved changes, and a sticky bottom bar — "You have unsaved permission changes." with Discard/Save buttons — that stays visible regardless of scroll position whenever the grid differs from what's saved. The in-card "Save Permissions" button is now also disabled when there's nothing to save. Added `unsavedPermissions`/`discardPermissions` keys to both `en.json` and `km.json`. Verified in-browser: toggle → sticky bar appears → Discard reverts and hides the bar; toggle → Save via the sticky bar → toast + bar disappears + change persists on reload.
